# ferens

[![ci](https://github.com/mel0k1/ferens/actions/workflows/ci.yml/badge.svg)](https://github.com/mel0k1/ferens/actions/workflows/ci.yml)
[![license](https://img.shields.io/badge/license-MIT-blue)](LICENSE)

Userspace-драйвер для видеокарт AMD поколения GCN4 на Rust. Идея такая: без своего модуля ядра, только sysfs, mmap и прямая запись в регистры Polaris. Документация AMD открыта, исходники ядра и Mesa тоже, поэтому каждая константа в коде сверена с реальными заголовками, а не придумана.

## Железо

| Кристалл | Карты | PCI ID из amdgpu_drv.c |
|----------|-------|------------------------|
| Polaris 10 (Ellesmere) | RX 470, 480, 570, 580, 590 | 0x67C0-0x67DF, 0x6FDF |
| Polaris 11 (Baffin) | RX 460, 560 | 0x67E0-0x67FF |
| Polaris 12 (Lexa) | RX 540, 550 | 0x6980-0x699F |
| VegaM | Radeon RX Vega M | 0x694C, 0x694E, 0x694F |

## Что уже работает

Скан PCI идёт через /sys/bus/pci/devices: читаются vendor, device, revision, распарсены BAR с флагами памяти. Регистровый BAR - наименьший memory-BAR (на Polaris это BAR2 на 256 КБ), апертура VRAM - наибольший; оба мапятся через mmap. Регистры доступны двумя путями: косвенно через пару MM_INDEX и MM_DATA (в байтах 0x0000 и 0x0004) и напрямую записью в BAR2 по смещению регистр*4 - второй путь и использует amdgpu, им же ходит compute-часть.

Конструктор PM4-пакетов собирает NOP, SET_SH_REG, SET_CONTEXT_REG, DISPATCH_DIRECT, INDIRECT_BUFFER, INDIRECT_BUFFER_CONST, WRITE_DATA, WAIT_REG_MEM и EVENT_WRITE. Заголовки type-3. У SET_SH_REG смещение регистра стоит первым словом тела. У DISPATCH_DIRECT порядок такой: dim_x, dim_y, dim_z, dispatch_initiator. Командное кольцо переносит пакеты через границу буфера и заполняет хвост однодвордными NOP.

Compute-очередь ставится через KFD, то есть через /dev/kfd и ioctl AMDKFD. Порядок такой: топология читается из /sys/class/kfd/kfd/topology/nodes, оттуда берутся gpu_id, PCI-адрес и минор render-ноды. GTT-память выделяется через ALLOC_MEMORY_OF_GPU и MAP_MEMORY_TO_GPU, хост-мапа делается mmap'ом render-ноды на тот же виртуальный адрес, что ушел в GPU, так что CPU VA и GPU VA совпадают. CREATE_QUEUE получает кольцо, страницу указателей и EOP; CP пишет read pointer в память через RPTR_REPORT_ADDR, а забор write pointer'а идет через WPTR_POLL_ADDR, поэтому и тот и другой лежат в нашей аллокации. На gfx8 doorbell - это 4 байта, слот очереди внутри среза процесса равен queue_id * 4, значение - write pointer в двордах. Завершение ловится фенсом: WRITE_DATA с WR_CONFIRM пишет магию в GTT, хост крутится на read_u32 с таймаутом.

Compute-очередь работает и без KFD - напрямую через регистры CP_HQD в MMIO, свой крейт ferens-mmio. Драйвер сам грузит микрокод MEC из /lib/firmware/amdgpu (polaris10/11/12_mec.bin, mec2 опционально): halt через CP_MEC_CNTL, слова в CP_MEC_ME1_UCODE_DATA под адресом из CP_MEC_ME1_UCODE_ADDR, в конце - запись версии ucode в UCODE_ADDR, потом halt снимается. HQD слота ME1 pipe0 queue0 выбирается через SRBM_GFX_CNTL (PIPEID [1:0], MEID [3:2], VMID [7:4], QUEUEID [10:8]) и программируется в том же порядке, что делает mqd_commit в gfx_v8_0.c: база PQ в единицах 256 байт, RPTR-репорт и WPTR-poll в байтах, CP_HQD_PQ_CONTROL с размером кольца (order_base_2 от двордов минус один), RPTR_BLOCK_SIZE 5, PRIV_STATE и KMD_QUEUE, квантум с EN/SCALE/DURATION, PRELOAD_SIZE 0x53 в persistent state, в конце CP_HQD_ACTIVE = 1. Активация KIQ-стилем, без MAP_QUEUES и без HWS: очередь сразу исполняет PM4.

RLC-микрокод грузится перед MEC тем же прямым способом, что и в gfx_v8_0_rlc_resume из v4.14 - в современных ядрах прямой путь у RLC исчез так же, как у MEC: его забрал SMU, поэтому референс тот же тег. Порядок такой: RLC выключается через RLC_CNTL.RLC_ENABLE_F32, serdes-юниты дожидаются простоя опросом RLC_SERDES_CU_MASTER_BUSY по каждому из четырех SE (polaris10/11/12 в amdgpu имеют max_shader_engines = 4) через GRBM_GFX_INDEX и дальше RLC_SERDES_NONCU_MASTER_BUSY по маске SE/GC/TC0/TC1; затем отключение clock и power gating (CGCG_EN/CGLS_EN в RLC_CGCG_CGLS_CTRL и RLC_CGCG_CGLS_CTRL_3D, RLC_PG_CNTL = 0), сброс через GRBM_SOFT_RESET.SOFT_RESET_RLC с паузой 50 мкс на фазу, для polaris11/12 - init_pg: clear state, save/restore-список и задержки PG (об этом дальше), слова микрокода пишутся в RLC_GPM_UCODE_DATA под адресом 0 из RLC_GPM_UCODE_ADDR, в конце в UCODE_ADDR уходит версия ucode и RLC_ENABLE_F32 = 1. Файлы - polaris10/11/12_rlc.bin; их заголовок - rlc_firmware_header_v2_0 с мажором 2, размером 104 байта и массивом ucode с 0x100, поэтому RLC-парсер принимает и major 1, и major 2 - общий блок заголовка у них совпадает. destroy гасит RLC последним, как gfx_v8_0_hw_fini, а перед ним возвращает clock gating в исходное состояние.


Память очередей - VRAM, без аллокатора: восемь колец по 4 КБ, MQD-тень, две таблицы страниц по 64 КБ (VMID0 и VMID1), блок clear state, страница кернела и мета-страницы слотов (rptr-репорт, wptr, кернарги, фенс, вывод) разложены в BAR0-апертуре начиная с 64 МБ, чтобы не задеть vBIOS-фреймбуфер; CPU пишет туда же через mmap этой апертуры. Раскладка: кольца 0x4000000 + слот*0x1000 (восемь штук до 0x4008000), MQD-тень 0x4008000, таблица VMID0 0x4009000 (8192 PTE), таблица VMID1 0x4019000, clear state 0x4029000, кернел 0x402B000, default page 0x402C000, мета-страницы слотов с 0x402D000 (по 4 КБ на слот). Слоты отображаются в движок как в ядре (gfx_v8_0_compute_ring_init): слоты 0-3 - ME1 pipe 0-3 queue 0, слоты 4-7 - ME2 (нужен mec2.bin, иначе open_queue отказывает), doorbell-слот = MEC_RING0 + номер слота, приоритеты - CP_HQD_PIPE_PRIORITY и CP_HQD_QUEUE_PRIORITY (high - pipe 2 и queue 15, как AMDGPU_GFX_PIPE_PRIO_HIGH и AMDGPU_GFX_QUEUE_PRIORITY_MAXIMUM), квант вытеснения - CP_HQD_QUANTUM = EN|SCALE(1)|DURATION(10). Каждый VMID получает собственную плоскую таблицу страниц: окно разбито на две половины по 16 МБ - identity-отображение VRAM [0x4000000, 0x5000000) и GTT [0x5000000, 0x6000000); VM_CONTEXTn_PAGE_TABLE_BASE_ADDR/START/END задают диапазон (START 0x4000, END 0x5FFF), PAGE_TABLE_DEPTH = 0 делает таблицу плоской, инвалимация через VM_L2_CNTL2 и VM_INVALIDATE_REQUEST с чтением RESPONSE, для VMID1 те же поля через VM_CONTEXT1_*. GTT-аллокация прописывает PTE в обе таблицы сразу, поэтому один и тот же GTT-адрес виден из очередей на обоих VMID. Write pointer доставляется дверным звонком, как у compute ring 0 в amdgpu: CP_MEC_DOORBELL_RANGE_LOWER/UPPER (KIQ и MEC_RING7) и CP_PQ_STATUS.DOORBELL_ENABLE, сама запись - 32-битный writel в BAR2 по смещению doorbell_index * 4. Поток диспетча перед настройкой кернела ставит COMPUTE_STATIC_THREAD_MGMT_SE0-3 в 0xFFFFFFFF - у только что запрограммированной очереди CU не разрешены иначе. Завершение ловится тем же WRITE_DATA-фенсом, у каждого слота своя мета-страница.

GTT - системная память, видимая GPU через ту же таблицу VMID 0. `ferens dispatch-gtt` аллоцирует страницу хоста: mmap с MAP_LOCKED и MAP_POPULATE, mlock, затем PFN каждой 4К-страницы читается из /proc/self/pagemap (нужен root, иначе PFN занулены). PTE системной страницы отличается от VRAM-ного битом SYSTEM (бит 1): VALID|SYSTEM|SNOOPED|READABLE|WRITEABLE против VALID|SNOOPED|EXECUTABLE|READABLE|WRITEABLE у identity-страниц - кодировка из amdgpu_vm.h. PTE пишутся прямо в таблицу в VRAM через апертуру, после чего VMID 0 инвалидируется. Кернарги, фенс и вывод живут в этой хост-странице: CPU кладёт буфер-дескриптор в свою память, CP пишет магию фенса и вывод по GTT-адресам, хост опрашивает фенс и читает результат у себя - ни одного чтения из BAR в цикле ожидания.

RLC-часть ведёт себя как PG-хост: внутри rlc-резюма, между сбросом и загрузкой микрокода, для polaris11/12 выполняется init_pg из gfx_v8_0.c - clear state, save/restore-список и задержки. CSB собирается из таблицы clearstate_vi.h (7 экстентов, 885 двордов значений, обёрнутых в PREAMBLE_CNTL/CONTEXT_CONTROL/SET_CONTEXT_REG/SET_CONTEXT_REG с PA_SC_RASTER_CONFIG/1 прочитанными из живых регистров/CLEAR_STATE - те же пакеты, что собирает get_csb_buffer) и кладётся в VRAM, RLC_CSIB_ADDR_LO/HI и RLC_CSIB_LENGTH на неё указывают. Save/restore-список берётся из самого rlc.bin: у заголовка v2 на 0x38-0x54 лежат reg_restore_list_size, reg_list_format_start, starting_offsets_start, размеры и смещения двух массивов; формат (первая часть - direct-список, RLC_FormatDirectRegListLength = 14 двордов) прогоняется через копию gfx_v8_0_parse_ind_reg_list с дедупликацией индексов, поток значений уходит в RLC_SRM_ARAM_DATA под RLC_SRM_ARAM_ADDR = 0, формат - в RLC_GPM_SCRATCH_DATA, туда же - размер restore-списка (дворды пополам) и десять стартовых смещений, уникальные индексы пакуются в пары RLC_SRM_INDEX_CNTL_ADDR_x (младшие 18 бит) и RLC_SRM_INDEX_CNTL_DATA_x (старшие 12). Дальше RLC_SRM_CNTL получает AUTO_INCR_ADDR и SRM_ENABLE, а задержки PG - RLC_PG_DELAY по 0x10 во все четыре поля, RLC_PG_DELAY_2.SERDES_CMD_DELAY = 3, RLC_AUTO_PG_CTRL.GRBM_REG_SAVE_GFX_IDLE_THRESHOLD = 0x55f0 и CP_RB_WPTR_POLL_CNTL.IDLE_POLL_COUNT = 0x60. У polaris10 этот путь в ядре пропущен (init_pg перечисляет только CZ/Stoney и P11/P12/VEGAM), поэтому у RX 580 ferens его тоже не делает - pg_initialized честно говорит false.

Поверх запущенного RLC `ferens gate` включает coarse grain clock gating: в RLC_CGTT_MGCG_OVERRIDE снимаются биты CGCG (3) и CGLS (4), serdes-юниты получают BPM-команды через RLC_SERDES_WR_CU/NONCU_MASTER_MASK = 0xFFFFFFFF и RLC_SERDES_WR_CTRL (cmd в битах 25:16, номер BPM-регистра в 31:28, BPM_ADDR 0xff и RSVD_BPM_ADDR - кодировка gfx_v8_0_send_serdes_cmd): сначала Clear CGCG_OVERRIDE (BPM-регистр 2), потом Set CGLS_EN (регистр 0); между командами serdes дожидается простоя по всем четырём SE. Финал - RLC_CGCG_CGLS_CTRL: золотое значение Polaris 0x0001003c (REP_COMPANSAT_DELAY 0xf, порог простоя 0x100) плюс биты CGCG_EN|CGLS_EN, итого 0x0001003f, у 3D-регистра - та же задержка и порог без EN-битов (его EN-биты в ядре не включают - там 3D-CGCG идёт через SMU), и CP_INT_CNTL_RING0 получает биты CNTX_BUSY/CNTX_EMPTY/CMP_BUSY/GFX_IDLE (18-21), которыми RLC узнаёт о простое графики. `ferens gate pg` дополнительно ставит в RLC_PG_CNTL биты STATIC_PER_CU_PG (3) и DYN_PER_CU_PG (2) - статическое и динамическое power gating CU-островов руками RLC. В amdgpu на Polaris всё это ходит сообщениями в SMU (gfx_v8_0_polaris_update_gfx_clock_gating), pg_flags стоят в ноль и до RLC-битов дело не доходит; ferens делает ровно тот регистровый путь, которым тот же код включает CGCG на Fiji/Carrizo - интерфейс у RLC один и тот же. destroy перед остановкой RLC гасит CG обратно (cg_off: override-биты возвращаются, четыре чтения CB_CGTT_SCLK_CTRL будят графику, обратные BPM-команды Set CGCG_OVERRIDE и Clear CGLS_EN, EN-биты снимаются).

Инициализация начинается с golden-регистров, до всего остального - сборки CSB, RLC, MEC: таблицы golden из gfx_v8_0.c и gmc_v8_0.c портированы дословно (17+8 записей для polaris10, 17+6 для polaris11/12 и gmc-таблицы на 5+4 записи - MC_ARB_WTM_GRPWT_RD и четыре VM_PRT_APERTURE_LOW_ADDR), семантика та же, что у amdgpu_device_program_register_sequence: тройка (offset, and, or), при and=0xffffffff - прямая запись, иначе read-modify-write. Для polaris10 поверх этого SMC-твик ixCG_ACLK_CNTL (0xc05000dc) через окно SMC_IND_INDEX/DATA (0x80/0x81): ACLK_DIVIDER = 0x18, как в ядре; i2c-твик для 0x67DF rev 0xc7 с конкретными subsystem id не портирован. Каждый массив слов, ушедший в GPU, проверяется чтением назад: после загрузки RLC-микрокода в окно RLC_GPM_UCODE, MEC1/MEC2 в CP_MEC_MEx_UCODE и CSB в VRAM через апертуру ferens читает слова обратно (адрес окна выставляется на каждое слово: автоинкремент окна на чтении нигде не задокументирован, UMR тоже адресует каждое слово) и сверяет CRC32 с полиномом 0xEDB88320; несовпадение - ошибка init, а не тихий мусор в SRAM. Перед каждой доставкой работы GPU видит свежие записи CPU: после записи PTE и перед doorbell'ом ставится HDP-флаш - запись 1 в HDP_MEM_COHERENCY_FLUSH_CNTL (0x1520) с readback, как vi_flush_hdp в vi.c. Диагностика: `ferens status` читает GRBM_STATUS (флаг GUI_ACTIVE), SRBM_STATUS и SRBM_STATUS2 (busy-биты VMC/MCB/SEM/IH/GCATCL2/BIF и SDMA/SDMA1) и VM_CONTEXT0/1_PROTECTION_FAULT_STATUS/ADDR/MCCLIENT с расшифровкой полей по gmc_8_1_sh_mask.h (PROTECTIONS [7:0], MEMORY_CLIENT_ID [20:12], MEMORY_CLIENT_RW [24] - read/write, VMID [28:25], mcclient печатается как четыре ASCII-символа) и сбросом через VM_CONTEXTn_CNTL2, как gmc_v8_0_process_interrupt; тот же дамп печатается при таймауте фенса в dispatch-mmio и dispatch-gtt. Последний предохранитель: если карта сидит в /sys/kernel/iommu_groups, dispatch/gate откажутся стартовать - DMA в системную память уйдёт мимо наших PTE; обходной лаз - FERENS_IOMMU_ALLOW=1.

Рядом с CP работает второй движок - SDMA, копирование данных без участия CPU. ferens грузит микрокод обоих инстансов - polaris10/11/12_sdma.bin и _sdma1.bin, у ядра на каждый инстанс свой файл (v4.10 sdma_v3_0_load_microcode): halt через SDMA0_F32_CNTL.HALT, слова через окно mmSDMA0_UCODE_ADDR/DATA (0x3400/0x3401, у SDMA1 шаг +0x200) с адреса 0, штамп версии, затем CRC32-верификация чтением назад, как у MEC. Кольцо GFX по 4 КБ на инстанс лежит в VRAM после CP-раскладки (0x4035000 и 0x4037000, мета с фенсом и writeback-указателем на 0x4039000, scratch-страница на 0x403B000): VIRTUAL_ADDR=0 и APE1_CNTL=0 - VMID0 без ATC, TILING_CONFIG = GB_ADDR_CONFIG & 0x70, RB_CNTL с полем RB_SIZE и RPTR_WRITEBACK_ENABLE, адрес writeback read pointer'а маскируется 0xFFFFFFFC, doorbell выключен - кик, как в ядре при use_doorbell=false, прямой записью в mmSDMA0_GFX_RB_WPTR, причём регистр держит смещение в байтах (wptr<<2), а read pointer читается с >>2. Формат пакетов у SDMA свой: LINEAR_COPY - op 1, sub 0, count, 0, src lo/hi, dst lo/hi, семь двордов ровно как в sdma_v3_0_ring_emit_copy, и FENCE - NOP, op 5, адрес, магия, как в ring_emit_fence; для пути с прерываниями за фенсом идёт TRAP - op 6 и context id (SDMA_PKT_TRAP_INT_CONTEXT), поднятый TRAP_ENABLE битом 0 в SDMA0_CNTL (0x3404), IV приходит с src_id 224. VM-контекст у SDMA тот же VMID0: раскладка VRAM-identity + GTT переиспользуется через общий program_vm0, GTT-аллокации SDMA живут во второй половине окна (курсор стартует со страницы 0x5800), чтобы не пересекаться с аллокациями CP. `ferens sdma-copy [bytes]` аллоцирует два GTT-буфера, заполняет источник паттерном, гоняет байты через VRAM-scratch (GTT→VRAM→GTT) двумя фенсами и сверяет результат на CPU.

Третий движок - графика. ferens грузит PFP/CE/ME из polaris10/11/12_pfp.bin, _ce.bin и _me.bin: halt тройкой битов CP_ME_CNTL (ME_HALT 0x10000000, PFP_HALT 0x4000000, CE_HALT 0x1000000), слова через три окна - CP_PFP_UCODE_ADDR/DATA (0xF814/0xF815), CP_CE_UCODE_ADDR/DATA (0xF818/0xF819) и CP_ME_RAM_WADDR/DATA (0xF816/0xF817) - каждый со штампом версии и CRC-верификацией, как у MEC. GFX-кольцо - 4 КБ в VRAM на 0x403B000, фенс и writeback rptr - на 0x403C000: CP_RB_VMID = 0, CP_RB0_CNTL с RB_BUFSZ = log2(размер/8) и RB_BLKSZ = bufsz-2, MTYPE 3 и MIN_IB_AVAILSZ 1, сброс WPTR при RB_RPTR_WR_ENA, адрес writeback в CP_RB0_RPTR_ADDR, пауза и повтор CNTL без WR_ENA, CP_RB0_BASE = адрес>>8 и BASE_HI = старшие биты, doorbell выключен RMW-ом DOORBELL_EN в CP_RB_DOORBELL_CONTROL - кик записью wptr в двордах в mmCP_RB0_WPTR, read pointer читается из CP_RB0_RPTR уже в двордах. Перед стартом CP_MAX_CONTEXT = 7 (max_hw_contexts-1), CP_ENDIAN_SWAP = 0, CP_DEVICE_ID = 1. Тест кольца - WRITE_DATA-фенс в память, ровно как gfx_v8_0_ring_test_ring; `ferens gfx-ring` прогоняет его и печатает rptr/wptr. До полного clear-state-потока из vi_cs_data (SET_CONTEXT_REG-секции, PA_SC_RASTER_CONFIG, CE-партиции из cp_gfx_start) - то есть до настоящей отрисовки - кольцо не доведено: для фенса графический контекст не нужен.

Прерывания идут через IH-кольцо в VRAM - 4 КБ на 0x403D000, writeback wptr на 0x403E000. Настройка снята с tonga_ih.c: INTERRUPT_CNTL2 = dummy page>>8, INTERRUPT_CNTL с выключенными IH_DUMMY_RD_OVERRIDE и IH_REQ_NONSNOOP_EN, IH_RB_BASE = адрес>>8, IH_RB_CNTL с RB_SIZE = log2(размер/4) (поле со сдвигом 1), WPTR_OVERFLOW_CLEAR и WPTR_WRITEBACK_ENABLE, MC_VMID = 0, адрес writeback в IH_RB_WPTR_ADDR_LO/HI, RPTR_REARM не ставится - он нужен только под MSI; запуск - RB_ENABLE и ENABLE_INTR той же записи, doorbell rptr выключен. Запись IV - 16 байт: src_id [7:0] дворда 0, src_data [26:0] дворда 1, ring_id/vmid/pasid из дворда 2, rptr и wptr меряются байтами и зацикливаются по размеру кольца; переполнение ловится битом RB_OVERFLOW в IH_RB_WPTR, ядро после очистки через WPTR_OVERFLOW_CLEAR стартует разбор с wptr+16 - то же делает ferens. Источники: у SDMA - trap из предыдущего абзаца, у compute - завершение диспетча: вслед за фенсом в кольцо пишется WRITE_DATA в регистр CPC_INT_STATUS (0x30B5) со значением 0x20000000 - та же связка, что в gfx_v8_0_ring_emit_fence_compute с комментом "src_id is 178", при включённом TIME_STAMP_INT_ENABLE в CP_ME1_PIPE0_INT_CNTL (0x3085, по биту на pipe) это рождает IV src_id 178. Оба пути показывает `ferens ih`: он отвязывает amdgpu, открывает SDMA и CP, биндит uio_pci_generic (modprobe при необходимости), включает bus master и INTx в командном регистре, гонит SDMA-копию с trap-пакетом и compute-диспетч с trigger-записью, на каждый interrupt читает /dev/uioN через poll, разбирает IV-записи из кольца и двигает rptr. Заодно исправлена давняя неточность в PM4: у WRITE_DATA поле count в заголовке было на единицу больше хартового (0xC004_3700 против 0xC003_3700 из PACKET3(WRITE_DATA, 3) в ядре) - пакет доедал лишний дворд за фенсом, на железе это маскировалось нулями в кольце; теперь все заголовки билдера сверены с посчитанными из ядерных макросов.

Путь под MSI - собственный модуль kernel/ferens_irq (C, out-of-tree, только мост): PCI-драйвер с таблицей Polaris-идов, в probe - pci_enable_device, pci_set_master, pci_alloc_irq_vectors(1, PCI_IRQ_MSI) и request_irq на вектор 0; обработчик лишь инкрементирует счётчик и будит waitqueue, никакой работы с регистрами - вся настройка IH остаётся в userspace через BAR-mmap, как в варианте с uio. Наверху cdev с /dev/ferens_irq0 и ioctl: WAIT (таймаут в мс, ядро снапшотит счётчик и уходит в wait_event_interruptible_timeout, возвращает -ETIMEDOUT или 0), COUNT, INFO (счётчик, номер вектора, флаг pci_dev_msi_enabled, PCI-identity) и RESET. RPTR_REARM в IH_RB_CNTL ставится только в этом режиме: под MSI IV-запись после прерывания не поднимет линию снова, пока rptr не продвинется, - то же условие, что в ядре (msi_enabled). Версионные гварды внутри: class_create с THIS_MODULE до 6.4 и без после. Сборка: make -C kernel/ferens_irq, insmod ferens_irq.ko; ferens сам биндит карту к драйверу (на выходе отвязывает, модуль остаётся загруженным), при отсутствии udev-ноды делает mknod по атрибуту dev из sysfs. Ожидание фенсов в wait-пути очередей идёт через trait IrqWait с двумя реализациями - FerensMod (ioctl) и UioDevice (poll): wait_fence_irq пересыпает 1 мс после каждого прерывания и перепроверяет фенс в памяти, так что лишний вектор (или прерывание соседнего слота) не ломает ожидание.

Живучесть и частоты. При таймауте фенса оба wait-пути (поллинг и прерывание) не просто печатают hang-отчёт (rptr/wptr слота, CP_HQD_ACTIVE и CP_HQD_DEQUEUE_REQUEST через SRBM_GFX_CNTL-мультиплексор, GRBM/SRBM-статусы, VM-фолты), но и сразу пытаются сбросить зависший слот: последовательность gfx_v8_0_deactivate_hqd(adev, 2) из ядра - CP_HQD_DEQUEUE_REQUEST = 2 (reset waves) под SRBM-мультиплексором, опрос CP_HQD_ACTIVE с таймаутом 200 мс, потом обнуление DEQUEUE_REQUEST, PQ_RPTR и PQ_WPTR; сброшенный слот выписывается из списка открытых и его можно открыть заново через open_queue. `ferens reset` показывает механику на живой карте: диспетч, фенс, hang-отчёт до и после сброса, повторный open_queue и второй диспетч на восстановленном слоте. Управление частотами - через SMC-канал сообщений: handshake снят с smu7_send_msg_to_smc (smu7_smumgr.c) - дождаться SMC_RESP_0 != 0, сбросить его записью нуля, написать номер сообщения в SMC_MESSAGE_0 (dword 0x94), дождаться нового ответа; 1 - OK, 0xFE - unknown command, 0xFFFF - прошивка не загружена; аргументы ходят через SMC_MSG_ARG_0 (0xa4). Перед работой ferens проверяет, что SMC-память жива, как smu7_is_smc_ram_running: бит ck_disable в ixSMC_SYSCON_CLOCK_CNTL_0 равен нулю и SMC PC >= 0x20100. Текущие частоты - PPSMC_MSG_API_GetSclkFrequency (0x200) и API_GetMclkFrequency (0x201), ответ в SMC_MSG_ARG_0 в единицах 10 кГц. DPM-таблица читается из SMC SRAM: SMU7_FIRMWARE_HEADER_LOCATION (0x20000) + смещение поля DpmTable в SMU73_Firmware_Header дают базу таблицы, GraphicsDpmLevelCount/MemoryDpmLevelCount - число уровней, SclkFrequency/MclkFrequency внутри уровней SMU73_Discrete_GraphicsLevel/MemoryLevel - частоты; смещения полей получены компиляцией smu73.h/smu73_discrete.h из ядра. Форс уровня - как smu7_force_dpm_highest/lowest: PPSMC_MSG_SCLKDPM_SetEnabledMask (0x145) и MCLKDPM_SetEnabledMask (0x146) с маской из одного бита; unforce - PCIeDPM_UnForceLevel (0x148) и загрузка полных масок. `ferens clocks` печатает таблицу уровней и текущие частоты, форсирует максимум и минимум и возвращает всё обратно unforce-ом; amdgpu при этом не отвязывается - команда работает на живой карте, как `ferens status`.

Полный soft reset - по той же схеме, что в ядре (check → pre → soft → post). Маски собираются по busy-битам: GRBM_STATUS (PA/SC/BCI/SX/TA/VGT/DB/CB/GDS/SPI/IA/IA_NO_DMA/CP/CP_COHERENCY) даёт SOFT_RESET_CP и SOFT_RESET_GFX плюс SRBM SOFT_RESET_GRBM, GRBM_STATUS2 (RLC_BUSY 0x1000000, CPF/CPC/CPG_BUSY) даёт SOFT_RESET_RLC и CPF/CPC/CPG, SRBM_STATUS - GRBM_RQ_PENDING → SOFT_RESET_GRBM, SEM_BUSY → SOFT_RESET_SEM, VMC_BUSY → SOFT_RESET_VMC и MCB/MCC/MCD-связка → SOFT_RESET_MC (только dGPU, как в gmc_v8_0_check_soft_reset), SRBM_STATUS2 - SDMA_BUSY/SDMA1_BUSY → SOFT_RESET_SDMA/SDMA1 (в ядре sdma_v3_0_soft_reset ставит их безусловно, ferens - только при busy). Сам сброс: GMCON_DEBUG (0xd5f) GFX_STALL|GFX_CLEAR, пауза 50 мкс, GRBM_SOFT_RESET (0x2008: CP 0x1, RLC 0x4, GFX 0x10000, CPF 0x20000, CPC 0x40000, CPG 0x80000) и SRBM_SOFT_RESET (0x398: SDMA1 0x40, GRBM 0x100, MC 0x800, SEM 0x8000, VMC 0x20000, SDMA 0x100000) с установкой битов, readback, паузой и снятием, GMCON обратно. Pre-фаза повторяет gfx_v8_0_pre_soft_reset: rlc stop, CP_ME_CNTL halt (CE/PFP/ME), deactivate_hqd(2) по открытым слотам, MEC halt, cg_off; пост-фаза пересобирает карту bring_up-ом целиком - золотые регистры, RLC/PG, MEC-микрокод, VM-таблицы, после чего очередь открывается и кернел проходит заново. VM fault отрабатывается отдельным сценарием: вывод кернела направляется на VA 0 (identity-окно VRAM с 0x4000000 размером 16 МБ, GTT-окно с 0x5000000, нулевая страница - пустой PTE), волна умирает по TLB-промаху, CP лочит VM_CONTEXT0_PROTECTION_FAULT_STATUS (0x536) независимо от включения прерываний, ferens опрашивает статус, печатает декод как gmc_v8_0_vm_decode_fault (protections, vmid, номер страницы в ADDR, read/write, ASCII-имя блока из MCCLIENT), чистит фолт через VM_CONTEXT0_CNTL2, сбрасывает слот и прогоняет корректный диспетч. Suspend/resume повторяет порядок amdgpu: движки глушатся до сохранения состояния - ih disable, SDMA0/1 stop_engine (RB+IB+F32 halt), CP_ME_CNTL и CP_MEC_CNTL halt, rlc stop, cg_off, затем pci_save_state - 256 байт config space в /var/lib/ferens/&lt;slot&gt;.bin; resume проверяет vendor/device снапшота, восстанавливает dwords 15..=4 (BARs, subsystem, INT), командный регистр пишет последним, как pci_restore_state, и делает полный bring-up с тестовым диспетчем. Полный сброс через sysfs - `ferens full-reset`: карта поднимается, диспетчится, и очередь остаётся активной на время сброса; методы сброса ferens показывает либо по sysfs reset_method (само ядро их заполняет, начиная с 5.15), либо обходом capability-списка config space (биты DEVCAP.FLR, AF-капа с TP|FLR, PMCSR NO_SOFT_RESET), после чего пишет 1 в sysfs reset - pci_reset_function ядра сам сохраняет и восстанавливает config space и прогоняет методы в порядке pci_reset_fn_methods (device_specific, acpi, flr с записью DEVCTL BCR_FLR и задержкой 100 мс, af_flr, pm через D3hot→D0, шинный сброс); факт сброса ferens проверяет канарками - CP_HQD_ACTIVE активного слота и MEC-халт в CP_MEC_CNTL, которые обязаны обнулиться, затем пересобирает карту bring-up-ом с нуля и повторяет диспетч.

Сам диспетч собирает такой поток пакетов: SET_SH_REG на COMPUTE_PGM_LO/HI (адрес кернела в единицах 256 байт), COMPUTE_PGM_RSRC1 и COMPUTE_PGM_RSRC2, COMPUTE_NUM_THREAD_X/Y/Z, COMPUTE_USER_DATA_0/1 (указатель на кернарги), затем DISPATCH_DIRECT и WRITE_DATA-фенс. Кернел - это 10 двордов рукописного ISA для gfx8: s_load_dwordx4 тянет буфер-дескриптор из кернаргов, buffer_store_dword пишет магию в память, s_endpgm. Дескриптор собран по таблице Buffer Resource из ISA-мануала GCN3: база 48 бит, stride в битах 61:48, num_records в третьем дворде, третье слово нулевое (TYPE=0 - buffer).

У CLI двадцать одну подкоманду. `ferens list` показывает найденные AMD-карты. `ferens show 01:00.0` читает CONFIG_MEMSIZE, нужен root. `ferens pm4-dump` печатает hexdump того же потока пакетов, что уходит в очередь, но офлайн - удобно сверять с ядром. `ferens dispatch` прогоняет демо-кернел на живой карте через KFD: печатает версию интерфейса, gpu_id, номер очереди, потом ждет фенс и показывает, что кернел записал в память. `ferens dispatch-mmio` делает то же самое без /dev/kfd: сам грузит rlc- и mec-микрокод, строит таблицы страниц обоих VMID, программирует CP_HQD слота 0 и запускает кернел через собственный дверной звонок. `ferens gate [pg]` включает CGCG/CGLS (с `pg` - ещё и power gating) поверх уже загруженного RLC и печатает RLC_CGCG_CGLS_CTRL и RLC_PG_CNTL до и после. `ferens dispatch-gtt` - диспетч с кернаргами и выводом в системной памяти через GTT. `ferens queues` - два слота разом: slot 0 на VMID0 с нормальным приоритетом и slot 1 на VMID1 с высоким, один и тот же кернел уходит в оба кольца, оба фенса дожидаются, вывод каждого слота печатается отдельно. `ferens gfx-ring` - загрузка PFP/CE/ME и фенс-тест графического кольца. `ferens ih` - полный interrupt-путь через uio: IH-кольцо, trap SDMA и EOP compute, разбор IV из /dev/uioN, фенсы дожидаются по прерыванию через IrqWait-trait. `ferens msi` - то же самое через собственный kernel-модуль ferens_irq: MSI-вектор вместо INTx, RPTR_REARM в IH_RB_CNTL, ожидание через ioctl с таймаутом. `ferens queues-irq` - два compute-слота разом с ожиданием фенсов по прерыванию: берёт ferens_irq, а при его отсутствии откатывается на uio_pci_generic, IH настраивается соответственно (REARM только под MSI). `ferens clocks` - управление частотами через SMC: таблица DPM-уровней, текущие sclk/mclk, форс максимума и минимума, unforce; root, без отвязки драйвера. `ferens reset` - dequeue-сброс слота 0 с hang-отчётами до и после и повторным диспетчем на восстановленной очереди. `ferens fault` - намеренный VM fault: диспетч с выводом на VA 0, страницу вне identity- и GTT-окон, опрос VM_CONTEXT0_PROTECTION_FAULT_STATUS, декод в формате gmc_v8_0_vm_decode_fault (protections, vmid, номер страницы, read/write, ASCII-имя блока из MCCLIENT), очистка через VM_CONTEXT0_CNTL2, dequeue-сброс слота и второй диспетч с корректным выводом - полный цикл детект/декод/recovery. `ferens soft-reset` - мягкий сброс карты: маски GRBM/SRBM_SOFT_RESET собираются по busy-битам, pre-фаза глушит RLC/GFX/MEC и деактивирует открытые HQD, сброс идёт через GMCON_DEBUG GFX_STALL/GFX_CLEAR с паузами 50 мкс, пост-фаза - полный ресетап и тестовый диспетч. `ferens suspend` / `ferens resume` - остановка и пробуждение: suspend глушит IH, SDMA0/1, GFX/MEC, RLC и CG (порядок amdgpu) и сохраняет 256 байт PCI config space в /var/lib/ferens/&lt;slot&gt;.bin, resume сверяет vendor/device снапшота, восстанавливает config (BARs раньше, командный регистр последним - как pci_restore_state) и делает полный bring-up с тестовым диспетчем. `ferens full-reset` - полный сброс через sysfs reset: детекция метода (reset_method ядра или capability-список), канарки CP_HQD_ACTIVE/CP_MEC_CNTL до и после, пересборка и тестовый диспетч. `ferens status` - дамп GRBM/SRBM-статусов и VM-фолтов с живой карты без поднятия очереди. `ferens sdma-copy [bytes]` - копирование через SDMA: два GTT-буфера, roundtrip через VRAM-scratch со сверкой на CPU.

Требования для dispatch: загруженный amdgpu с amdkfd (это штатный путь ядра, своего модуля ferens не ставит), доступ к /dev/kfd и к render-ноде - обычно хватает группы video или render, root не обязателен. Ядра новее 4.20. Требования для dispatch-mmio, gate, dispatch-gtt, queues, gfx-ring, ih и sdma-copy жёстче: root (BAR в sysfs открывается только им, PFN из pagemap - тоже), amdgpu не должен держать карту - драйвер видит биндинг через симлинк driver и отказывается работать, и в /lib/firmware/amdgpu должны лежать rlc-, mec-, sdma-, sdma1-, pfp-, ce- и me-файлы под чип; для `ferens ih` дополнительно нужен модуль uio_pci_generic (ferens сам его подгружает и биндит, а на выходе отвязывает). Для `ferens msi` и `ferens queues-irq` нужен свой модуль ferens_irq: make -C kernel/ferens_irq (нужны kernel-headers под запущенное ядро), insmod ferens_irq.ko; ferens сам биндит карту к драйверу, а на выходе отвязывает, модуль оставляет загруженным - одна карта на инстанс модуля. Тестов 175, среди них сверка заголовков пакетов с эталонными словами из ядра, сверка каждого слова ISA-кернела с энкодингами из LLVM-тестов, сверка слов HQD, таблицы страниц, разбора заголовков микрокода и полной последовательности записей RLC-резюма и init_pg в порядке ядра, SDMA-пакетов и конфигурации SDMA-кольца, окна загрузки ucode обоих SDMA-инстансов, GFX-кольца и трёх окон загрузки PFP/CE/ME, маппинга слотов в me/pipe/queue/doorbell, настройки IH-кольца, разбора и дрейна IV-записей с обходом по кольцу и обработки переполнения, wait-петли по прерыванию, ioctl-номеров с раскладкой структуры ferens_info против макросов ядра, SMC-канала (handshake, коды ответов, чтение DPM-таблицы и форс-масок на реактивном фейковом баре), сборки busy-масок soft reset из GRBM/SRBM-статусов и последовательности GMCON/GRBM/SRBM-записей на фейковом баре и сохранения/проверки PCI config снапшота и обхода capability-списка config space (FLR/AF-FLR/PM-детекция, NO_SOFT_RESET, зацикленная цепочка кап). CI гоняет fmt, clippy с -D warnings и тесты.

## Чего нет

RLC: jump table и cp table не программируются - в ядре они создаются только на Carrizo/Stoney. MGCG/MGLS (medium grain) и light sleep не трогаются: на Polaris amdgpu гонит их через SMU-сообщения, включён только coarse grain и RLC-биты PG; само rail-переключение питания остаётся за SMU. SMU-канал читает частоты и форсирует уровни, но дальше этого не идёт: нет записи DPM-таблиц обратно в SMC SRAM (populate/upload из smu7_hwmgr.c), VddC-запросов, thermal-управления (температура и вентилятор), FreezeLevel-обновления таблиц и OD/OW-расширений - всё это требует копирования больших структур через SMC-окно и пересчёта ватта-вольтовых зависимостей. GTT - фиксированное окно 16 МБ и VRAM-раскладка без аллокатора общего вида; VMID больше единицы не используются - таблицы VM_CONTEXT2..7 есть в железе, но ferens их не программирует, у полноценного процесса была бы своя таблица и свой GTT-регион. Прерывания поднимаются двумя путями: uio_pci_generic на INTx (ferens ih и откат в queues-irq) и собственный модуль ferens_irq на MSI (ferens msi, основной путь queues-irq). Модуль - мост, а не драйвер: он берёт на себя только PCI-probe, один MSI-вектор и waitqueue с ioctl (WAIT с таймаутом, COUNT, INFO, RESET), всю работу с MMIO, IH-кольцом и IV-записями ведёт userspace через свои BAR-mmap, как в варианте с uio. Раскладка ferens_info (u64 count, u32 irq, u32 msi, u16 vendor/device) проверена тестом против макросов _IOW/_IOR. Модуль держит одну карту на инстанс, второй в probe отказывает с EBUSY. Dequeue-сброс восстанавливает compute-слоты; мягкий сброс карты (GRBM/SRBM_SOFT_RESET) закрывает весь GC-блок с SDMA и VMC по busy-маскам: в ядре sdma_v3_0_soft_reset ставит SDMA-биты безусловно, ferens - только при busy в SRBM_STATUS2, чтобы не трогать простаивающие движки; при занятой SDMA биты выставятся так же. Post-ресетап повторяет bring_up целиком, поэтому все открытые слоты и GTT-буферы после soft reset не выживают - их создают заново. Suspend не уводит карту в PCIe D3: power state остаётся за ядром и ACPI, ferens глушит движки и сохраняет config space - состояние сохраняется между вызовами suspend/resume, но не через перезагрузку. Полный сброс идёт через sysfs reset, то есть через PCI-слой ядра: ferens не эмулирует device_specific и acpi-методы и не делает D3cold (нужен ACPI _PR3 у платформы) - он выбирает тот путь, который выберет ядро, и проверяет результат канарками; при шинном сбросе (SBR) рядом стоящие устройства той же шины тоже сбросятся. Реакция на VM fault демонстрируется намеренным диспетчем на пустую страницу: волна умирает по TLB-промаху, CP лочит статус, фенс не приходит - ferens опрашивает статусы, декодирует, чистит и восстанавливает слот; отдельного interrupt-пути для VM fault (src_id 223) нет, фолт ловится поллингом. У SDMA doorbell-режим и power gating движка не включаются, кик идёт MMIO-записью WPTR. GFX-кольцо работает в тестовом режиме - фенс проходит, но clear-state-поток, CE-партиции и настоящий вывод на экран не сделаны, для графики дальше нужен DCE-стек.

MMIO без root падает с EPERM, это ожидаемо: файлы resourceN в sysfs открывает только root.

## Структура

- ferens-core - PCI-скан, mmap BAR, MMIO через index/data и напрямую, биндинг uio_pci_generic с ожиданием прерываний через poll и модуль ferens_irq с ожиданием через ioctl
- ferens-gfx8 - регистры gfx8, коды PM4, конструктор пакетов, кольцо, ISA-кернел, сборка диспетча
- ferens-kfd - /dev/kfd: ioctl, топология, GTT-аллокатор, compute-очередь, doorbell
- ferens-mmio - MEC-, RLC-, SDMA- и GFX-микрокод с CRC-верификацией, golden-регистры, до восьми compute-очередей через CP_HQD с приоритетами и двумя VMID, таблицы VMID0/1 с GTT, clear state и SRM, CGCG/PG, HDP-флаш, диагностика VM-фолтов, IOMMU-гвард, SDMA-копирование, GFX-кольцо и IH-кольцо с разбором IV в VRAM, dequeue-сброс слотов и SMU-канал частот
- ferens - CLI

## Сборка

Linux обязателен, код под unix-only. Компилятор закреплён в rust-toolchain.toml на версии 1.100.0.

```
cargo build --release
cargo test --all
make -C kernel/ferens_irq    # модуль прерываний, нужны kernel-headers
```

Сборка модуля ferens_irq не входит в cargo-сборку: make вызывает kbuild из /lib/modules/$(uname -r)/build, полученный ferens_irq.ko грузится insmod-ом перед `ferens msi` (или ferens найдёт его сам по cwd-пути kernel/ferens_irq/ferens_irq.ko).
